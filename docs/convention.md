## 프로젝트 개발 규칙

- 도메인 주도 설계(DDD)를 바탕으로 업무 규칙을 모델링한다.
- 업무 규칙을 추가하거나 변경할 때는 실패하는 테스트를 먼저 작성하고,
  구현으로 통과시킨 뒤 필요하면 리팩터링한다.
- Spring Modulith를 사용해 모듈 경계를 관리한다. 모듈 간 연동에는
  공개 API 또는 이벤트를 사용한다.


## 프레젠테이션 계층 (presentation)

- 컨트롤러, HTTP 요청·응답 DTO, 예외 응답 변환 코드를 둔다.
- 컨트롤러는 요청 형식을 검증하고 요청 DTO를 애플리케이션 명령으로 변환한다. 서비스 실행 결과를 HTTP 상태 코드와 응답 DTO로 변환
한다.


## 애플리케이션 계층 (application)
- 유스케이스를 실행하는 서비스와 서비스의 입력·출력을 표현하는 Command·Result를 둔다.
- 서비스는 필요한 객체를 조회하고, 도메인 메서드를 호출하고, 처리 결과를 저장한다. 여러 작업이 하나의 유스케이스에서 함께 성공하거나 실패해야 한다면 해당 유스케이스에 트랜잭션 경계를 둔다.
- 서비스의 Command와 Result는 application 패키지에 각각 독립된 최상위 타입과 파일로 선언한다. 이름에는 유스케이스와 역할을 드러낸다(예: RegisterMemberCommand, RegisterMemberResult). 등록 결과가 ID 하나여도 Result로 반환한다.
- 입력 객체인 Command에는 어떤 호출 경로에서든 필요한 값만 검증한다.


## 도메인 계층 (domain)

- 도메인 모델, 업무 규칙, 도메인 모델의 저장·조회에 필요한 레포지토리 인터페이스를 둔다.


## 인프라 계층 (infrastructure)

- 레포지토리 구현체, Spring Data JPA 인터페이스, 외부 시스템 연동 구현을 둔다.
- 도메인 모델과 JPA 엔티티를 분리해 JPA 엔티티와 두 객체 사이의 매핑을 인프라 계층에 둔다.


## 계층별 테스트

- presentation — HTTP 상태 코드, 응답 본문, 오류 응답을 확인한다. 예를 들어 서비스 응답을 Mockito로 설정해 신규 예약과 기존 예약 반환을 각각 검증한다.
- application — 실제 서비스로 유스케이스 결과를 확인한다. 재요청 시 재고가 한 번만 감소하는지처럼 저장 상태까지 확인해야 하는 동작은 테스트 DB를 연결해 검증한다.
- domain — 도메인 객체를 직접 생성해 상태 전이와 업무 규칙을 확인한다. 만료 규칙은 고정 시각으로 만료 직전과 정확한 만료 시점을 검증한다.
- infrastructure — 커스텀 쿼리, 매핑, 락처럼 DB 동작에 의존하는 부분은 테스트 DB에서 확인한다.


## 검증 책임

- HTTP 요청 DTO에서 필수 입력의 누락, 공백, 길이, 형식, 요청 범위를
  Bean Validation으로 검증한다.
- Command : 호출 경로와 관계없이 유스케이스 실행에 필요한 입력 조건을
  생성 시 검증한다. 예를 들어 멱등성에 필요한 requestId의 누락을 확인한다.
- application : 리소스 존재 여부, 권한·소유권, 저장소 조회가 필요한 중복 여부를 확인한다.
- domain :  유효한 초기 상태, 허용되는 상태 전이 등 자신의 상태와 업무 규칙을 보장한다.
- 모든 경로에서 지켜야 하는 업무 규칙은 도메인에서도 보장한다.
- HTTP 요청 DTO의 Bean Validation은 잘못된 요청을 거절하는 데 사용한다.
