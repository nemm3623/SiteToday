# Git 작업 흐름

## 1. 이슈에서 완료 조건 정하기

- [이슈 양식](../.github/ISSUE_TEMPLATE)에서 기능 제안, 버그 보고, 개발 작업 중 목적에 맞는 양식을 선택한다. 버그는 재현 절차, 실제 결과, 기대 결과를 함께 기록한다.
- 완료 조건은 관찰할 수 있는 동작으로 작성한다. 예를 들어 “정원이 한 자리 남은 공고에 서로 다른 두 근로자의 배정 요청이 동시에 들어오면 한 건만 성공하고, 저장된 배정 인원은 정원을 넘지 않는다”처럼 작성한다.
- 작업 중 범위 밖의 개선점을 발견하면 변경 이유와 예상 영향을 설명하고 사용자와 범위를 합의한다.

## 2. 작업 브랜치 만들기

- 작업 전 현재 브랜치와 `git status`를 확인하고 다른 작업의 변경 사항이 섞이지 않도록 한다.
- 기본 브랜치에서 이슈 단위로 브랜치를 만든다. 이름은 `<유형>/<이슈번호>-<짧은-설명>` 형식을 따른다. 예시는 `feat/42-assignment-capacity`다.

## 3. 커밋 작성하기

- 메시지는 `<유형>: <변경 요약>` 형식으로 작성한다. 예시는 `fix: 동시 배정 시 공고 정원 초과 방지`다.
- 브랜치와 커밋 유형은 기능 추가에 `feat`, 버그 수정에 `fix`, 내부 구조 개선에 `refactor`, 테스트에 `test`, 문서에 `docs`, CI 변경에 `ci`, 기타 유지보수에 `chore`를 사용한다. GitHub 라벨의 `feature`, `bug`, `maintenance`는 각각 `feat`, `fix`, `chore`에 대응한다.
- 함께 검토하거나 되돌릴 수 있는 변경을 한 커밋에 담는다. 기능과 그 기능을 검증하는 테스트는 함께 담을 수 있다.
- 에이전트는 사용자가 요청한 경우에만 커밋, 푸시, 브랜치 삭제를 수행한다.

## 4. 완료 조건 검증하기

- 업무 규칙을 바꿀 때는 [개발 규칙](convention.md)에 따라 실패하는 테스트를 먼저 작성한다. 개발 중에는 변경 영역의 테스트를 실행하고, Java 코드 변경을 PR로 제출하기 전에는 저장소 루트에서 `./gradlew test`를 실행한다.
- DB 락이나 트랜잭션 동작을 검증했다면 사용한 DB, 실행 조건, 저장 결과를 기록한다. 문서만 변경했다면 링크 확인 등 변경에 맞는 검증을 수행한다.

## 5. PR 작성과 병합 전 확인

- [PR 템플릿](../.github/pull_request_template.md)에 변경 이유와 관련 이슈를 적는다. 병합으로 종료할 이슈는 `Closes #42`, 참고할 이슈는 `Refs #42`처럼 연결한다.
- 이슈의 완료 조건별로 실제 실행한 명령과 관찰한 결과를 연결한다. 동시 배정 사례라면 성공한 요청 수와 처리 후 DB에 저장된 배정 인원을 기록한다. 실행하지 못한 검증은 사유와 남은 위험을 적는다.
- 리뷰어의 판단이 필요한 설계 선택과 이유를 적는다. API·기능 또는 프로젝트 진행 현황이 달라지면 [진행 현황](progress.md)도 갱신한다.
- 병합 전 이슈의 완료 조건, 검증 결과, 미해결 리뷰 의견을 확인한다. CI 도입 시 이 문서에 필수 검사와 통과 조건을 추가한다.

## 반복 작업의 스킬 도입 기준

실제 PR에서 같은 판단 절차를 반복해 설명하게 되면 프로젝트 스킬로 정리한다. 첫 후보는 이슈의 완료 조건, 코드 변경, 테스트 결과를 대조해 PR 본문 초안을 작성하는 작업이다. 단순한 입력 누락은 템플릿을 보완하고, 매번 같은 명령으로 판정할 수 있는 검사는 테스트나 CI에 둔다.
